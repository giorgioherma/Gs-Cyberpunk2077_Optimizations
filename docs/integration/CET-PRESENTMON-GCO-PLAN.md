## Rules that apply to every stage

1. **Do not disturb the working Capture page.** Preserve one game folder, two pages, three stage cards, CET/GRSP F11 capture, optional PresentMon, QPC alignment, native elevated PresentMon observer, one UAC, tray/reopen, Collect/Restore, journal and rollback. Do not add a new profiler, new installer, second monitoring path, new required user action or a new workflow.
2. **Maintain ownership.** CET repository owns its existing Lua Resolver/Generator, generic/native/semantic transforms and G-GC. GCO owns orchestration, cross-domain reporting, presentation and eventual combined packaging. GRSP owns REDscript instrumentation; REDscript optimization is deliberately **out of scope** here. Do not fork or duplicate the mature CET generator into GCO. If a CET report/generator contract needs improvement, make a tested upstream CET-owner change and then pin the new vetted source for GCO; do not add a corrective postprocessor.
3. **Keep standalone CET/CapFrameX working.** PresentMon becomes the frame-evidence source for GCO, **not** a mandate to remove CapFrameX inputs from standalone CET or GRSP. Never fabricate CapFrameX JSON in order to use existing readers.
4. **Single .NET 10 runtime.** Adapt the Resolver's existing .NET 8 desktop packaging to use GCO's one private .NET 10 Core/Desktop runtime, preserving all source-owned files, embedded resources, semantic library and runtime templates. Check real dependencies and provenance. No second private CLR or wholesale import of a historical self-contained Resolver ZIP.
5. **Captured data is sealed evidence.** `RESULTS/GCO-Capture-.../collection.json` hashes are authoritative. Work in a separate derived/staging directory; never mutate the collected archive or indexes. Resolver can write its own generated JSON only into staging. Live game source discovery is read-only; no files written into installed mods during analysis/generation.
6. **Frame metrics must be semantically truthful.** Use actual official PresentMon 2.6.0 headers/data and GCO's already-approved CET+GRSP F11 intersection and GRSP QPC/Unix anchors. Distinguish frame intervals, CPU busy, GPU busy/time, frame-generation/displayed semantics, and absent PC latency/drop fields. Mark unavailable data `NOT_CAPTURED` / null, never 0 by default; no fixed timezone, no invented matches/causation or added CET+GRSP CPU totals. G-GC authorization fails closed without defensible measured frame headroom.
7. **Preserve CET's source-safe pipeline exactly:** generic 0-Engine → native integration → generic finalization → source-aware semantics. Untouched, partially optimized and fully optimized installations must work. Idempotence, safe drift rejection, lifecycle/callback preservation, dependencies and actual generated Lua/native assets require substantive tests; no fixed mod list or source hash as runtime inventory.
8. **One canonical Windows CI:** `.github/workflows/build-windows.yml`. On this development branch run the existing `workflow_dispatch` manually when implementation needs testing; its automatic push trigger remains `main`. Extend its real integration/contract tests, **do not add another workflow**. Full package output/verification stays authoritative. Preserve GCO v1.2.5 until explicitly told otherwise.
9. **Do not prematurely freeze the build.** Existing verified GRSP native cache may be reused; other compiled inputs can be cached only when source SHA, toolchain, scripts/configuration, transitive inputs and complete provenance match, with proven cold-cache and cache-hit equivalence. Never skip validation merely because cache exists.
10. **Documentation is part of implementation.** Every meaningful work session must update [progress ledger](CET-PRESENTMON-GCO-PROGRESS.md) and `docs/LATEST-WORK.md`: exact changes, commit/branch, tests and run URL, pass/fail, known uncertainties, stage status and next action. Update `docs/HANDOFF/CORE.md`, decisions or architectural contracts when the behavior/ownership decision materially changes. Never mark a stage complete from source-only changes, screenshots or a green build that did not exercise that stage's output.

## Stage 1 — Integrate the complete existing CET Resolver and baseline it on .NET 10

**Goal:** GCO's development package can launch the **actual, unmodified-behavior CET Resolver** and parse its baseline output, without changing PresentMon or the Capture page.

**Implementation:** Use the pinned CET source checkout already acquired by GCO CI (`vendor-cet`), extend the canonical `integrations/three-profiler-test/Build-Test.ps1 -Integrated` to publish the existing `src/G.CETResolver.App` and its own core/knowledge/0-Engine runtime assets as a .NET 10 framework-dependent component. Preserve its CLI (`--capture`, `--game`, `--json`, optionally `--generate-pass`), ownership, current source compatibility, G-GC semantics and the existing generator implementation. Keep historical CET CapFrameX parsing unchanged for this first baseline. Record exact CET source pin, source assets, executable/core identity and bundle manifest. Any required retargeting must stay reproducible and owner-safe; do not copy an old self-contained .NET 8 package.

**Stage-gate proof:** one runtime/manifest/package test; real Resolver executable launches against a representative **known-good CET capture in a disposable analysis copy**, emits parseable expected JSON; baseline functionality and key output remain consistent with CET owner behavior, including error and empty-source handling. No writes to original capture or installed mods. Only then mark Stage 1 **PASS**.

## Stage 2 — Provide a real PresentMon frame-time handoff to the CET analysis owner

**Goal:** The existing CET reporting/calibration layers consume correctly interpreted **GCO-aligned PresentMon** frame evidence rather than requiring CapFrameX JSON for GCO analysis.

**Implementation:** In GCO, produce one canonical validated frame chronology from sealed `PresentMon/PresentMon.csv` plus established source F11 marker proofs; preserve exact input rows, clocks, frame counts and units. Provide a tested, versioned input contract to the existing CET owner reporting/hitch-calibration code, extending the **CET source owner** where necessary. Preserve the CET report's frame percentiles, FPS, thresholds, sustained hitch episodes/toll, cross-owner/time-window correlations, callback `callsPerFrame`, scenario stats and G-GC frame-headroom safety. Do not infer CapFrameX-only data (PC latency or unproven dropped/frame-type flags). Preserve standalone legacy CapFrameX reader and never modify GCO's successful collection/trimming semantics.

**Stage-gate proof:** use actual PresentMon 2.6.0 header/sample rows plus malformed/empty/missing/unaligned/legacy scenarios, independent numerical reference for percentiles/hitch episodes, QPC/Unix monotonic correspondence, missing metric semantics, no phantom correlations, accurate G-GC calibration/fail-closed behavior, and identical original capture hashes before/after. Log any metric that cannot be mapped equivalently. Stage 2 **PASS** only when end-to-end CET report consumes the real interface.

## Stage 3 — Wire read-only Page 2 CET analysis to a sealed GCO capture

**Goal:** user presses Continue into the existing ANALYZE page and GCO invokes CET Resolver in **a separate analysis workspace**, using current live source and captured CET/GRSP/PresentMon evidence without accidental archive mutation.

**Implementation:** Enforce existing verified restoration/preflight before analysis. Build a staged CET input using owner APIs, not hand-edited `CET_Resolver_Input.json` as a false source of truth. CET Resolver runs read-only against current effective CET mod source; GCO presents truthful per-owner diagnostics and captures missing data/exclusions, with optional contextual GRSP evidence but no REDscript optimization. Keep the original two-page UI and game-path-only workflow, and leave generation disabled while source proof is incomplete.

**Stage-gate proof:** validate sealed hash/index preservation; identity and provenance of live mods; mismatch/replaced source detection; already-optimized/partially-optimized/untouched detection; empty/partial/absent optional PresentMon; Resolver nonzero exit/timeouts/errors; repeat analysis gives stable results; Game/Restore/Capture controls are unchanged. Stage 3 **PASS** only after a packaged GCO workflow exercises real report production and safely refuses unsupported inputs.

## Stage 4 — Validate CET generation and prepare the REDscript handoff

**Goal:** finish the **CET side** inside GCO, not the REDscript optimization project or the final combined CET+REDscript release.

**Implementation:** Invoke the existing source-owned CET `--generate-pass` in isolation and inspect actual generated files. Prove untouched-source generation, partial completion, idempotent second pass, dependencies, 0-Engine/native stages, ZIP game-relative path topology, and source-drift refusal. Preserve per-mod ownership and source provenance, never write directly to game installation. GCO's eventual combined ZIP interface must accept the CET contribution without treating this CET-only milestone as final product completion. Leave REDscript optimizer and final CET+REDscript composition explicitly **NOT STARTED**.

**Stage-gate proof:** verified actual ZIP entries and reproducible source-safe output, Lua/native content contracts, pristine→partial→completed/idempotent variants, rollback/exclusions, real native/CET interaction smoke where available, packaged .NET10 integration, full original Windows CI, and **separate real gameplay acceptance** when gameplay behavior is claimed. Any incomplete critical validation remains **BLOCKED**, not a pass. Stage 4 **PASS** makes the CET side *handoff-ready* only.

## Stop line — REDscript is a separate project

Once Stage 4 passes, **stop planning/implementing additional work in this four-stage feature**. Record exactly what GCO exposes to a future REDscript optimizer: immutable verified GRSP evidence, aligned frame chronology, read-only source discovery contracts, CET candidate/owner results, safe overlay ZIP contribution schema, and unresolved prerequisites. Open a new, separately approved REDscript design/implementation plan when its turn comes. Do not interpret Stage 4 as permission for REDscript generics, new semantic catalog, full-stack REDscript generator, or final combined release. The original product's eventual **one game-relative combined ZIP** remains the final goal, not a promise that Stage 4 already delivers it.

## Execution and reporting discipline

- Before starting work, read [progress ledger](CET-PRESENTMON-GCO-PROGRESS.md). Never advance a stage merely because the previous one was planned; collect its acceptance evidence and report blockers.
- Use statuses **NOT STARTED → IN PROGRESS → PASS** or **BLOCKED**. A failed CI, test, dependency or gameplay validation remains recorded; do not quietly overwrite historical failures.
- Update both progress ledger and `docs/LATEST-WORK.md` **in the same source milestone commit** where practical, or immediately after the exact CI outcome becomes known. Include precise branch, SHA, run URL, tests, output fixtures and real-play status; no artificial progress percentages.
- Tests should target real failures and real generated output, not text-token assertions or decorative UI coordinates. A fully green CI does not establish gameplay success.
- No changes on `main` or merge until explicitly approved after verified stage evidence. No product version bump, new workflow, new caching policy or unrelated Capture/UI changes.
