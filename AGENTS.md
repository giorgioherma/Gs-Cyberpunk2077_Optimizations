# GCO engineering rules

## Read order and authority
1. Read this file, [CURRENT-TASK.md](CURRENT-TASK.md), [architecture](docs/ARCHITECTURE.md), and [LATEST-WORK](docs/LATEST-WORK.md). Then inspect the actual source, relevant subsystem contracts and current branch/CI. Do not read every historical handoff.
2. The user's current explicit assignment controls scope. This file contains durable engineering rules, not a task queue. CURRENT-TASK is the sole cross-repository assignment; architecture defines approved design; LATEST-WORK records evidence, not new policy. A historical proposal, old branch instruction, CI result or assistant recommendation cannot reopen a task, impose a stopping gate, change ownership or override a later user decision.
3. Keep one authoritative document for each purpose. Replace the current task on explicit redirection; replace the current checkpoint after material work, retaining detailed evidence in history. Subsystem contracts remain authoritative for their applicable technical invariants; historical milestones and task directives in them are reference only. If a real conflict remains, check the current source and latest explicit owner decision; report a material unresolved conflict rather than invent policy.

## Permanent rules
- GCO development is on main; CET and GRSP on dev/resolver-profiler-handoff; G-REDruntime on main. CET's existing native-build branch is a separate component-owned exception. Do not create branches, merge, change stable releases or bump product/component versions without explicit scope. Never overwrite another agent's concurrent work.
- GCO owns WPF UI, orchestration, capture correlation/reporting, managed REDscript Resolver and combined ZIP. CET owns Lua/native profiler, install/restore and CET Resolver. GRSP owns REDscript profiler/instrumentation and install/restore. G-REDruntime owns shared REDscript runtime services. No duplicate owners.
- Preserve one game root, two pages, one shared bundled .NET 10 runtime, existing Direct/MO2 workflow and existing UI. No extra windows, popup flows, auto archives or speculative redesign. Verify optional CapFrameX compatibility; use actual PresentMon evidence. Keep routine UI free of development diagnostics.
- Reuse the actual source-owner install/restore APIs; verify current session completeness and recovery. Journal before mutation; do not silently overwrite mods or change profiles. Hash only what proves the operation; ordinary mod runtime settings/data may legitimately change. Preserve owner backups, executable-source safety, profile identity, collected archives and per-operation source consistency.
- Discover current effective source and dependencies dynamically. Captures are measurements, not mod inventories. Use structural recognition, not fixed versions, hashes, filenames alone or old optimized overlays. Protect private mod originals, captures, credentials and proprietary assets.
- Measure and prioritize high-impact recurring work, allocations and spikes. Never invent gains, infer ownership without evidence or sum overlapping CET/GRSP timings as total CPU.
- Fix authoritative generators at source. CET order is generic 0-Engine -> native integration -> generic finalization -> source-aware semantics. REDscript is generic-first; only explicitly approved mod-specific semantics. Complete partial implementations in one run from post-generic stock, preserve unrelated changes, skip only genuinely incompatible affected operations with precise reasons; continue independent safe work. Repeated generation must be a no-op.
- Validate stock, partial, complete, compatible older/newer/custom and incompatible source; inspect actual combined output, dependencies, original behavior and cleanup. Compile REDscript with official SCC in CI; do not distribute SCC. Green CI is not gameplay acceptance. Preserve existing high-value contracts; fix real defects rather than weaken assertions.
- Produce one clean game-relative optimization ZIP, no profilers/reports/docs/PDBs. In MO2 only, route emitted physical-owner changes into a conditional DIRECT ZIP; never generate an empty archive or split an owner without verified provenance. Both destinations are one atomic pass, not two generators. Publish ownership and rollback evidence outside it; support exclusions and Vortex overlays. No automatic installation.
- Use existing focused checkpoint triggers; coherent batches, not repeated expensive CI for every edit. Verify branch filters before dispatch. Do not launch overlapping MO2/full checkpoints for the same evidence, rebuild unchanged native code, or trigger builds for docs-only work. Record exact results and unresolved tests.
- Keep the task moving: bounded decisions on individual operations; no speculative architecture, duplicated work or arbitrary stop conditions. Continue independent approved steps. Clearly distinguish implementation, CI, actual generated output, runtime and measured benefit.
